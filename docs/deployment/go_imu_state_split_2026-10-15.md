## 文件与职责

```text
fsm/
├── fsm.h                       通用State基类、FSM状态容器
├── deployment_context.h        共享数据（不是状态）
├── deployment_states.h/.cpp    RobotFSM注册、切换和安全检查
└── states/                     全部具体状态；各文件只实现本状态
    ├── stand_state.h/.cpp       唯一StandState：go_stand与真机FSM共用
    ├── passive_state.h/.cpp     PassiveState：趴下→到位确认→卸力
    ├── ppo_state.h/.cpp         PPOState：策略目标与增益交接
    ├── hold_state.h/.cpp        HoldState：初始保持与站姿保持
    ├── fault_state.h/.cpp       FaultState：故障零目标
    └── amp_state.h             AmpState抽象接口，暂不实现/注册/调用
```

所有具体状态都直接继承 `State`，统一在 `go_fsm::states` 命名空间。不存在第二个StandState，也没有兼容别名或位于目录外的旧状态实现。总FSM只组织这些状态，不再包含具体状态类定义。

唯一的StandState提供两种构造入口：独立go_stand传入起点/终点/StandSettings，保留等待0＋回车及25/0.5；真机FSM传入DeploymentContext，进入Stand即按部署配置运动、增益60/2。两者执行同一份站起计算代码，不再用一个状态包装另一个状态。

Passive自行实现趴下运行、到位确认、卸力；PPO自行实现策略交接；Hold和Fault只实现自身行为。五次曲线公式继续共用 `function/my_myth`，Stand通过原SmoothTrajectory数值封装使用它；这些数学工具不是状态、不参与FSM注册。

总FSM不包含AmpState头文件、不创建AMP对象；键2仅返回“AMP未开放”，没有调用AMP状态。保留FaultState是为了继续满足原故障锁定/卸力行为。

## 自己设置站立和趴下角

编辑 `imgo2_deploy/go_imu/config/deployment.yaml` 中两个独立参数：

```yaml
deployment:
  # 其他参数保持；以下每行一条腿：FL、FR、BL、BR。
  # 每行3个角：髋、大腿、小腿，单位rad，逻辑输出侧。
  stand_pose: [0.0, 0.87, -1.82,
               0.0, 0.87, -1.82,
               0.0, 0.87, -1.82,
               0.0, 0.87, -1.82]
  crouch_pose: [0.0609119907, 1.17687547, -2.87996769,
               -0.0609119907, 1.17687547, -2.87996769,
                0.0609119907, 1.17687547, -2.87996769,
               -0.0609119907, 1.17687547, -2.87996769]
```

文件中已经列出这些值，可以直接改对应关节。不要另加一个deployment节点，应修改原节点内的字段。

两组角都为**硬件顺序**，不额外加offset/方向/减速比，不经过policy_to_hardware再次重排。省略时构造函数提供默认站姿及原启动角生成的趴下值；正式YAML已显式填写，以方便独立修改。

站立目标不再从PPO的 `default_dof_pos` 取值。后者仍是策略观测和动作的训练参考姿态，不随stand_pose改变；现用fsm_check以stand_pose作为PPO的固定模拟反馈（旧ppo_check已删除）。改变固定站姿不能证明策略适合这个姿态，PPO真实效果仍需验证。

原 `HIP/THIGH/SHANK_START_OFFSET` 与限位宏保持原样。自定义趴下角不改变下一次进程启动的归零依据；若自定义趴下与初始机械姿态不同，重启前仍需回到初始化所要求的姿态。

## Passive具体行为

```text
StandHold/PPO下按9＋回车
  → 状态名LieDown：从当前反馈角执行crouch_s秒五次轨迹
  → 轨迹结束，继续用60/2等待实际反馈到位
  → 全部12关节的位置和速度连续满足条件
  → 状态名Passive：KP=KD=前馈tau=目标dq=0，卸力
```

从PPO退出时仍在默认0.5秒内把当前增益平滑过渡到60/2，同时执行默认8秒轨迹。正常卸力条件现在由反馈决定，不只靠轨迹时间：

| deployment参数 | 默认值 | 用途 |
|---|---|---|
| `crouch_position_tolerance` | 0.05rad | 所有关节相对crouch_pose的最大允许误差 |
| `crouch_velocity_tolerance` | 0.5rad/s | 所有关节速度绝对值上限 |
| `crouch_settle_s` | 0.2s | 位置/速度条件连续满足的时间；不满足则重新计时 |
| `crouch_arrival_timeout_s` | 2s | 从轨迹结束起允许等待反馈到位的最长时间；必须大于settle时间 |

因此默认理想到位确认在8秒轨迹结束后再持续0.2秒，约8.2秒卸力。轨迹结束后等待期间仍输出最终目标及60/2；到2秒截止仍未达标，则报告 `crouch arrival timeout` 并进入Fault，走原全部总线卸力和锁定流程。

正常Passive卸力后保持通信和健康检查，不停止线程、不重新归零；目标q保留合法的趴下参考值，但KP/KD/tau/dq均为零，不产生PD或前馈控制力。它不同于故障锁定：正常Passive可以按0＋回车，从当时实际测量角重新站起，增益从零平滑恢复到60/2；按1无效，要先站起。

卸力后机身可能受重力继续运动，软件不会用60/2把它拉回目标；本轮没有接触传感器判断，也不能保证硬件零控制时完全没有机械阻力。实机的支撑、到位阈值和卸力效果仍需确认。

## 构建与配置生效

本轮在工程内 `go_imu/build` 构建全部目标。仍需GO_IMU_BUILD_RL=ON和已有Torch/yaml-cpp。

从go_imu目录运行时，推荐明确指定源配置，避免读到build旁的旧副本：

```bash
cmake --build build -j2
./build/rl_real_imgo2 --check-policy --policy-dir ./policy --config ./config/deployment.yaml
```

实际真机入口使用相同参数去掉 `--check-policy`，本轮未执行真实设备启动。运行中的参数不热更新；改YAML后重启，改C++宏需重新编译。完整操作见 [控制手册](go_imu_control_flow_2026-10-15.md)。

## 同日结构纠正记录：删除双StandState与继承套层

现象：首次拆分后保留了根目录旧stand_state，又在states内放了一个派生于MotionState的新StandState；MotionState内部再创建旧StandState。HoldState也仍放在states外，PPO/Fault继承它。这没有满足“所有状态归入states，每个文件只负责自己状态”的要求。

根因：把保留原go_stand行为错误地实现成保留另一套状态类，而不是让两个入口共用一个实现。

本轮修正：合并成唯一 `states/stand_state.h/.cpp`；删除 `fsm/stand_state.h/.cpp`、`fsm/motion_state.h/.cpp`；将 `fsm/hold_state.h/.cpp` 移入states并取消其作为其他状态父类的职责。更新stand_main、原站立测试、CMake和文档引用，未保留别名/旧头文件壳。旧文件曾被入口/CMake/文档引用，已同步迁移；早期JSON源码哈希记录保留为历史快照，不冒充当前文件清单。

验证：工程内Release重新构建，31/31 CTest通过（48.12秒），覆盖独立stand、部署站起/PPO/Passive、零增益卸力和超时、策略检测、搬出构建。源码枚举确认只有一份stand_state.cpp；全部具体State派生类均位于states且直接继承State。关闭RL依赖的独立go_stand构建及stand_fsm测试结果见根README维护记录。关节宏、部署姿态配置、模型未改，无硬件运行。

待确认：本轮只纠正结构，真实映射/频率/到位阈值/卸力与再次站起效果仍待DEPLOY-13，不把离线回归标成实机通过。


## 同日方案评估：到中间姿态卸力，再由重力落稳

用户拟将Passive卸力目标改为大腿1.166rad、小腿−2.77rad（已更正，最初误说1.66不作为最终建议），目的是避免向原完整趴姿继续施加PD，因编码器/姿态误差顶紧。髋保持现有配置。本轮仅使用临时YAML评估，不改正式deployment.yaml、启动姿态宏、状态代码或策略。

相对当前源配置大腿1.17687547rad、小腿−2.87996769rad，新目标变化分别约−0.01087547rad（−0.62°）和+0.10996769rad（+6.30°）。两者处于当前逻辑限位−0.9～2.87、−3.0～−0.733rad内；这仅说明软件范围合法，不能证明没有机械干涉或机身已接近地面。

区分三件事：

- crouch_pose可以定义为“卸力前的中间姿态”，不必与start_pose_rad相同。当前算法可执行到该姿态再卸力，无需改变状态结构。
- 现有Passive不是驱动失能/断电：到位后kp=kd=tau=dq=0，仍保持FOC通信和反馈。减速器摩擦/机械阻力仍可能存在，不能保证必然靠重力到达某个精确角度。
- 机械启动宏仍表示下一次初始化时实际摆放的姿态，不能为改变卸力位置而顺手更改。一次运行内卸力后按0会从最新反馈角起步；下次重启必须先恢复与启动宏一致的机械姿态，避免归零基准错误。

当前正常卸力条件依旧是：完成8秒轨迹，各关节实际位置误差≤0.05rad、速度绝对值≤0.5rad/s连续0.2秒，然后置零控制量；不是目标刚下发就卸力，也不是仅到计时点就无条件正常卸力。结束后2秒仍未到位会进入Fault并卸力。因此中间目标本身仍应可达、无挤压；若先接触限位，等待期间仍有60/2控制，不能靠这个改动替代归零检查。

重力落稳可作为机械上验证的方案，但当前没有机身触地/支撑接触检测；需要确认卸力时机身已接近支撑面、剩余落差小、足腿无卡住/挤压，并用支架或吊带约束首次试验落差。未知摩擦、重心、脚地接触、机身碰撞会改变卸力后的动作。不能只据该两角承诺会平缓落到原趴姿；也不能通过改目标角修复真正的编码器零点错误。

验证：更正后的临时配置已通过rl_real_imgo2 --check-policy（未打开设备），覆盖模型/参数及固定轨迹预检。更正候选的完整fsm_check键盘回归通过，含站起/PPO/2秒回站/趴下到位卸力/再次站起、终端恢复等；使用理想模拟反馈，不包含重力/碰撞仿真。本轮不把临时配置写入源文件；旧数值1.66的中途检查不作为最终候选验证证据。

已完成：明确新目标在软件范围内、现有到位卸力机制可复用，区分中间卸力姿态/机械启动姿态/FOC零控制量。待确认：真实重力落稳的方向、落差、接触/限位裕量与卸力效果，需受控机械实测；源配置是否最终采用该候选尚未代为修改，仍由README DEPLOY-13跟踪。
