# 确定目标/反馈错位属于哪一段：测量与改进方案

2026-10-21。用户要求明确此前7.5–10ms目标/估算力矩对齐线索，以及角度是否也有问题，给出确定和改进方法。本轮只复核已知协议/记录限制并制定方案；没有修改控制、增益、超时或运行硬件，以下实验全部待执行。

## 1. 要分别确定的量

1. **命令等待/发送交付**：策略/上层产生目标后，多久才真正出现在485线上。
2. **反馈交付**：电机发出反馈后，多久主机读到、解析并交给策略。它仍不包含未知内部采样/滤波时间。
3. **真实关节动态**：目标已经应用后，关节以什么带宽/阻尼跟踪，负载和接触如何改变它。
4. **遥测通道动态**：反馈tau可能有估算/滤波，q/dq也可能有不同处理；一个tau对齐量不能统一赋给q、dq和IMU。

此前10ms不是已确认的故障，也不是准确的物理延迟。**如果只有tau遥测慢，真实执行和q反馈都及时，正确处理可能只是修日志配对/遥测模型，不应该为了“补偿10ms”改控制。** PD公式本身不带固定10ms延迟；真实驱动实现、电流控制、机械和遥测可以有动态。

## 2. 第一步：在正在跑的新批量版本只加记录

先取得对应新283秒运行的批量收发源码。本机仍是旧逐台exchange，不在旧版上盲目加测试后声称验证新版本。

统一主机steady_clock纳秒，数据在事件发生时固定，不在写日志时重算。各电机记录硬件索引/总线/ID；每次发布本地主机command_seq与每轮bus_round_seq：

| 事件 | 必须保存的内容 | 能确定什么 |
|---|---|---|
| 推理输入快照 | 真正45维obs、previous_action、每设备接收/序号、状态代次 | 输入和action确实配对 |
| 推理完成/目标发布 | raw/clip后action、目标、增益、command_seq、时间 | 结果等待与目标覆盖 |
| 总线取目标 | 实际取得的command_seq，限幅/offset/方向换算后的具体17字节报文 | 总线是否发送了日志说的那份目标 |
| 每条写入开始/完成 | bus_round_seq、ID、字节数、steady时间 | 主机排队与write耗时；完成不等于线侧发完 |
| 读取与完整有效帧解析 | chunk到达时间、ID/CRC/原始16字节、q/dq/tau、反馈本地序号、解析时间 | 接收/解析/发布时序，错误ID/重复/旧帧线索 |
| 发布快照/策略消费 | 引用的反馈序号、接收时间、最新目标序号 | 是否过晚发布、沿用旧快照或读取错字段 |

当前17字节请求/16字节反馈格式没有主机command_seq回显字段，本地序号只是主机记账，不能当作电机“已应用此命令”的确认。三条请求/三份反馈仍必须按有效ID分发，不能仅凭48字节或读入顺序绑定。

记录异步输出，预分配并保留丢样计数；修真实输入配对和trace安全发布，保留所有超时/CRC/故障锁定。不靠每周期printf或同步刷盘测延迟；先比较记录开关是否显著改变时序。

验收：能够沿同一个command_seq还原发布→总线取得→写入，以及每个feedback_seq的解析→发布→消费；没有未来反馈、错ID和跨轮混用。输出给电机的目标/增益与未加诊断版本一致。

## 3. 第二步：逻辑分析仪配合主机记录，先确定传输段

沿用已获得正确解码的采集方式，识别同一条总线的三个ID、请求/回复帧头及CRC；每条总线内部测请求出线、反馈出线，确认真实碰撞/间隔及批量结构。主机另保存对应写/读时间，有必要时加原始usbmon。

- 请求在主机产生后很晚才出线：查目标发布、线程周期/调度、USB OUT交付。
- 请求出线后电机很晚才回复：查电机协议应答、485方向/冲突和设备内部行为。
- 反馈已经在线上结束、主机过一段时间才看到：查USB IN短包交付、驱动/TTY及读取线程。
- 主机已解析，策略仍拿旧反馈：查批量快照发布、锁、序号、控制/推理取样。

分析仪与主机时钟不是自动同步的，不能直接减不同设备的绝对时间。使用可辨识且受控的报文序列与触发/公共标记对齐，检查时钟漂移；无可靠对齐时只比较各时钟内的时间间隔，给出能证明的边界。

这一步不要求关节明显运动，可先在既有稳定受支撑姿态验证通信；具体发送控制量依现有安全流程，不在没有新代码审查时连发未知运动命令。

## 4. 第三步：不用PPO做受控的小幅动态响应验证

用户已经验证固定目标25/.5受载不抖，不重复做同一静态结论。需要的是受限小幅、平滑、低激励的动态跟踪：有支撑的单电机/单腿，先确定机械余量和停止条件，使用当前已验证的参数，从低频/低幅开始，出现振荡即停止。不要整机承重直接扫到已观察到的7–8Hz，也不直接重放完整行走目标。

记录实际发送目标和对应q/dq/tau，至少比较两个方向和几档低激励响应；保持增益、负载等条件一次只变一项。使用有限非周期平滑序列或多档频率交叉验证，避免单一周期信号互相关差一个周期却被当固定延迟。

分别看：

- 目标变化到tau变化：命令应用、电流/力矩和tau遥测的综合关系，不能仅凭tau推断真实电磁力矩。
- 目标到q：幅值衰减、过冲、相位随频率/负载的变化；机械跟随必然非瞬时，不能把全部相位解释为反馈通讯延迟。
- q差分与dq：单位、符号、滤波和时间相容性，主机快照异步/重复必须处理。

可用“纯延迟+低阶动态”作描述模型，与单纯时间平移比较，但不能仅凭一个闭环运行唯一分解所有因素。若要严格确定q是否是10ms前的物理位置，需要独立位置参考或已知设备内部采样时间；例如有同步时标的外部编码测量。普通低帧率视频无法分辨毫秒级延迟，高帧率视频也须考虑帧间隔与同步误差。

同时询问厂商/核对固件：反馈tau是电流估算、命令值还是滤波值，q/dq/tau是否同内部采样时刻、滤波更新周期是多少、请求到命令生效与回复的顺序。这是区分“tau遥测慢”与“执行慢”的必要信息来源之一。

## 5. 按结果改进，而非统一补偿10ms

| 确定的原因 | 对应改进 | 不应直接做 |
|---|---|---|
| 只存在日志/快照错位 | 保存真实引用的目标/反馈序号与事件时间，离线正确配对 | 把所有反馈时间戳减10ms冒充新鲜数据 |
| 主机目标排队或反馈晚发布 | 使用最新完整目标/状态，减少不必要等待，保持按ID解析和一致快照；测P95/P99 | 无条件提频/缩短超时或清空输入丢回复 |
| USB/串口交付延迟 | 在测量定位后处理驱动/桥接或更换有证据支持的通信路径 | 仅凭4Mbps或高速USB认定延迟足够小 |
| tau遥测滤波较慢 | 文档化其时标/滤波，分析时建模，必要时获取更原始通道 | 以遥测lag给整个PD做前馈超前补偿 |
| 真实动态跟踪/触地振荡 | 同步实测执行器、限矩、接触与时序到仿真，再分项评估增益/动作平滑或重训鲁棒性 | 只调Kp或套用仿真稳定就声称实机稳定 |
| IMU独立参考显示动态误差 | 查安装、融合和滤波/同步，按测量建模 | 行走时屏蔽IMU/关节反馈做消融 |

仿真应分别表示命令应用与反馈交付，且与真实链路同端点比较。当前1.5ms反馈开关仅覆盖一段；先完成上述分解，再决定是否需要新增命令延迟/执行器模型。既有7.5–10ms拟合量不能与反馈年龄、1.5ms事务全部相加。
