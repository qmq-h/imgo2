## 1. 镜像项的符号问题

设置位置：`base_move/rough_env_cfg.py:135–139`；实现：`velocity/mdp/rewards.py:275–294`。保存env.yaml同样启用了该项，weight=-1。

当前对角配对FR↔RL、FL↔RR，所有hip/thigh/shank都直接平方相减；仅看髋部分，直立时的惩罚为：

```text
P_hip = [(q_FR - q_RL)^2 + (q_FL - q_RR)^2] / 2
r_hip_mirror = -1 * P_hip
```

当前模型四髋轴均为+X，外展的逻辑角度是左腿q、右腿-q。于是：

- 前左外展：q_FL>0；当前镜像项把q_RR拉向同样的正值，这对应后右内收。
- 前右外展：q_FR<0；当前镜像项把q_RL拉向同样的负值，这对应后左内收。

### 用原函数运行的反例

通过AST提取未修改的`joint_mirror`函数，在有命名关节的独立Torch张量上执行；直立度门=1，大腿/小腿均为默认值，相互完全相等。结果：

| 姿态，hip按FL/FR/RL/RR顺序 | 髋角 rad | raw镜像误差 | 加权贡献（未乘dt） |
|---|---|---:|---:|
| 四髋默认零位 | 0, 0, 0, 0 | 0 | 0 |
| 前外、后内 | +0.3, -0.3, -0.3, +0.3 | **0** | **0** |
| 四腿均向外 | +0.3, -0.3, +0.3, -0.3 | **0.36** | **-0.36** |

说明当前项没有表达“相同外展程度的物理镜像”，也不保证站姿合理。零位也有零误差，所以此项**不会单独强迫所有策略必然饱和**；一旦别的目标推动前髋外展，它会为后髋提供朝内收方向的压力。

若需要左右对角髋的物理镜像，应单独使用髋角相加的误差（默认角均为零时）或先转换到统一外展符号再比较；不能把所有关节都统一改为相加，大腿/小腿仍需分别核对。是否需要对角同步、在转向/复杂地形时如何门控，也应与零位姿态约束分开决定。本轮仅指出语义和修改方向，未改实现。

### 为什么会一直卡在边界

- 对环境而言，原始-4、-20、-78经过裁剪都变成-3，目标都是-0.375 rad。回报很难区分这些裁剪外数值。
- `action_rate_l2`罚的是环境收到的裁剪后相邻动作之差。若长期维持-3，单看这一维变化惩罚为0；它不限制持续偏置，也不约束Actor原始均值的绝对值。
- 高斯熵随std增大而增大；均值足够远离边界时，std很大仍可让绝大多数执行动作保持同一侧的裁剪极值。此时原始分布熵高，不代表执行器有有效、多样的探索。
- 这是动作裁剪后的回报平台与高斯分布/熵正则共同形成的风险，不是“PPO概率比clip_param=0.2直接把关节夹住”。也不能简单说裁剪让所有PPO梯度归零：PPO用log-prob更新，并非直接沿动力学穿过clamp求梯度。

本机高斯Actor/PPO实现与包装器源码支持上述机制；训练服务器实际RSL包版本不由当前本机版本代替证明。checkpoint的std与代表输入的Actor输出则是直接读取到的事实。没有独立消融，不能把此次均值/std变化全部归因于entropy_coef一个参数。

## 5. 为什么原策略能好，以及推荐的具体改法（建议，尚未实施）

原`policy_now.pt`的准确训练run/奖励/模型尚未找到，不能把当前rough配置当成它的实际训练配置，来源限制见 [原策略核对](../deployment/ppo_stairs_confirmation_2026-10-26.md)。即使假定原策略也有同样的角度同步项，四髋接近零时镜像误差也为零，因此它完全允许正常零位附近的策略存在；这项风险不会迫使每次训练都进入同一种姿态。随机初始化、地形与其他目标的相互作用可能使训练进入不同区域，尚无成对训练验证。

对角腿的摆动/支撑相位同步，不等价于把三个关节原始角度全部绑为相等。大腿/小腿的前后摆动可保留当前对角配对；髋承担横向平衡、站宽、横移和转向，建议先让它独立适应，并用默认角软约束防止长期内外偏置。这样无需修改公共`joint_mirror`函数，也不会改变其他任务的函数语义。

```python

self.rewards.joint_mirror.weight = -1.0
self.rewards.joint_mirror.params["mirror_joints"] = [
    ["FR_(thigh|shank)_joint", "RL_(thigh|shank)_joint"],
    ["FL_(thigh|shank)_joint", "RR_(thigh|shank)_joint"],

# 四髋默认角为0；允许转向/横移时偏离，但持续偏置要付出代价。
```

## 6. 探索的直观解释与机身高度的权重竞争

网络针对每种观测给出动作均值mu，训练用`mu + sigma * 标准正态随机数`尝试周围动作，再按采样所得轨迹的优势更新概率分布；并非每轮固定增大一个关节，也没有“训练轮数越大探索越合理”的规则。部署确定性JIT输出均值，不采这个随机噪声。

高斯探索方法本身常见，当前后髋学出的分布相对于执行边界已退化。例如一个示意的温和探索mu=.5/sigma=.2，大约95%的原始动作落在.1–.9，执行后仍有差别；而本次代表静站后左髋可近似为mu=-78/sigma=22，大约95%落在-122至-34，执行时全被裁成-3。由此可以同时出现“原始熵很高”和“执行动作几乎不探索”。这不表示优化器有意寻找坏姿态，也不意味着PPO概率比裁剪错误；实际收益区分不足与熵正则/缺少分布边界共同允许该结果。

### 高度低是实际姿态差异

前进.5m/s时base原点高度原策略28.71cm、最新25.26cm。最新后膝平均约-2.19rad，原策略约-1.96rad，并伴随后髋内收；这套更折叠的腿形与更低机身一致。新策略保存的高度目标仍为0.30m，不是配置目标被改成了0.25m；旧策略原训练目标未知。

高度奖励是软目标：`-10*(h-.30)^2`。h=.25时只扣.025（未乘公共dt），并不是扣10分；所有项一起乘dt=.02，没有单项漏乘步长。只要其他目标的收益抵消这个代价，较低姿态仍可能被保留。

### 足端目标-.20本身可以合理，关键是测量点与支撑/摆动门控

**同日修正**：先前简化算例将FOOT link原点与球心混同，按脚中心高.022m推导了7.8cm净空及25cm两项少扣分；这两个具体数值不适用于当前模型，现已更正。`feet_height_body`使用FOOT link原点；净空评测使用碰撞球底部，二者不是同一个点。当前URDF碰撞球心在FOOT局部偏移[-.008,±.0035,-.020]m，默认姿态FK下球心比FOOT原点低约.02108m。

机身.30m、FOOT原点相对机身z=-.20m时，该原点世界高.10m；若足端保持名义方向，球底净空约`.10-.02108-.022=.05692m`，而非7.8cm。足端朝向会继续改变该换算，所以不能用一个机身系link高度目标直接代替地形净空。

当前`feet_height_body`没有接触/摆动门控，并用`foot_velocity - root_velocity`加权。世界中不滑动的支撑脚，也会因机身前进而得到非零权重。降低机身能让该脚的机身系link z更接近-.20，因而仍可形成向低姿态的优化压力。

修正后的**仅两项示意**：平地直立、扫描有效、vx=.5m/s，两只支撑脚世界静止，FOOT原点固定为名义FK中脚球触地时的世界高度.04308m，速度权重tanh(2*.5)=.7616；省略其余脚、奖励和姿态变化：

| 机身高度 | 高度项weight=-10 | 两支撑脚feet_height_body项weight=-5 | 两项合计 |
|---|---:|---:|---:|
| .30m | 0 | -.02468 | -.02468 |
| .275m | -.00625 | -.00776 | **-.01401** |
| .25m | -.02500 | -.00036 | -.02536 |

该简化比较支持“存在偏低压力”，不再支持“25cm比30cm少扣分”的先前算例；27.5cm在这两项中少扣分，也不是实际完整策略的最优高度。用同一固定足端方向/世界位置只是隔离定义影响，不能当作25–30cm所有真实姿态的精确几何或整套训练回报。修正计算与原始FK数据见 [站姿方案JSON](ppo_stand_entry_plan_2026-10-27.json)。

另有既存代码风险：`base_height_l2`对全批射线做any NaN/Inf判断，一处异常使整批回退到root_link_pos_w；当前本机Isaac数据接口的root_pos_w是root_link_pos_w的别名，因此该分支会把整批高度误差置0。历史服务器训练中触发频率未记录，不能认定它曾持续失效。

`feet_height_body`的命令门控在静站时关闭，所以不能用这一项直接解释静站机身偏低；静站要结合策略已经形成的髋/膝偏置、默认角软约束及静止样本覆盖评估。优先修正支撑/摆动定义、高度有效性和后髋分布，再对高度权重作受控对照；目前没有经过短训验证的“正确高度weight”。

## 8. 为什么mu能到-78，能否从奖励直接看出来

**mu不是总奖励**：mu是当前观测下策略动作分布的均值，12关节就有12个分量；“mu约-78”特指某个代表观测下的后左髋分量。总奖励是各项`dt*weight*func`之和，训练用它构造回报/优势再更新网络。它影响mu如何学习，但不是mu本身。训练step_dt与部署循环的区别见 [频率核对第5节](../deployment/deployment_frequency_audit_2026-10-21.md)。

本轮直接读取当前JIT的forward代码：obs_normalizer为Identity；mlp最后一层是`torch.linear(input, weight, bias)`；deterministic_output也是Identity。均值输出路径没有tanh或±3裁剪。原始mu由网络权重和观测计算，可以超出执行范围；执行裁剪发生在它之后。

因此，mu=-78不是reward配置、关节角或限位，也不是所有观测下都等于-78；它是此前明确保存的代表站立45维输入下，后左髋网络输出的近似值。名义默认站姿下同checkpoint约为-69.91，状态不同输出就不同。JSON保存本轮读取的原始JIT代码和权重哈希。

当前物理奖励计算接收到的是裁剪后的动作/随后产生的物理状态：关节位置、机身高度、接触、速度、动作差等。它们不能直接分辨某次原始动作-4、-20还是-78（这些动作裁剪后都是-3；带随机分布时整体执行概率仍可能不同）。PPO的概率/log-prob计算知道mu与sigma，但环境reward没有直接对原始mu的幅值或越界惩罚。因此能从配置与函数看出允许越界漂移的机制，**不能仅凭reward值推导出为何恰好为-78，也不能证明哪一项奖励贡献了多少漂移**。

在训练早期，增加某一侧动作的概率可能提高回报；进入执行饱和后，继续把均值推远带来的物理回报差异会减弱。有限样本、优势估计、共享网络更新以及变化的sigma都可能继续改变某些状态下的mu。checkpoint序列证实越界随训练加深，但要定位具体更新原因仍需分布/裁剪/优势统计与消融。

特别澄清：无压缩高斯的`H=log(sigma)+常数`，熵不直接依赖mu；熵项直接作用于sigma，不能说熵正则直接把mu推到-78。修正物理姿态奖励和在算法分布/优化loss中约束原始均值，是不同层次的处理；即使新增环境action_l2，若仍在裁剪后计算，也不能直接区分-4和-78。任何新增优化项或有界分布需要在实际训练RSL版本里实现并验证，本轮未实施。

## 9. base_height与feet_air_time的奖励/惩罚符号

当前控制dt=.02s，RewardManager对所有项统一计算：`r_i = dt * weight_i * func_i`。正负含义要结合函数返回值，不能只根据weight命名奖励或惩罚。

### base_height_l2

扫描正常、直立时，函数返回非负的`(h-.30)^2`，h为机身相对扫描地面的高度；乘weight=-10后总是非正。它通过少扣分鼓励接近30cm：

| 高度h | 原始误差平方 | 乘weight=-10 | 再乘dt=.02的单步贡献 |
|---|---:|---:|---:|
| .30m | 0 | 0 | 0 |
| .25m或.35m | .0025 | -.025 | -.0005 |

该项每个控制步结算，0是最佳值，没有“到目标必须给正分”的要求。当前自定义函数实际读取robot根位置；虽然配置给asset_cfg.body_names指定base，函数没有用body_ids选择任意link高度，不能把改body_names理解为已切换测量部位。

### feet_air_time

weight=+1，但函数在首次触地的控制步返回`sum((last_air_time-.5)*first_contact)`；没有新落地的脚不计入，指令范数<=.1时整体关闭，另乘直立度门。只看一只新落地脚、门控为1：

| 刚结束的滞空时间 | 函数返回值 | 单步贡献（weight=1，dt=.02） |
|---|---:|---:|
| .15s | -.35 | **-.007** |
| .50s | 0 | 0 |
| .60s | +.10 | **+.002** |

所以它是以.5s滞空为分界的有符号激励：不足门槛扣分，超过门槛加分；不是“只要抬脚就加分”。threshold单位是秒，指单脚离地到落地的时长，不是完整步态周期，也不是采样周期。它倾向延长滞空，但不保证总奖励下最终实现.5s滞空。

高度项每步结算，air_time项按落地事件结算，两者量纲和发生频率不同；不能只看weight的-10与+1，或只看某个落地瞬间的值就断言哪个主导。此处为源码和算术解释，没有修改两项奖励。
