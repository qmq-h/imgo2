# 运行日志说明（robot.csv / policy.csv / events.log / meta.json）

> 位置：每次运行一个目录 `log/<YYYY-MM-DD_HH-MM-SS>_<pid>/`（`log/` 已在 `.gitignore` 里）。
> 开启方式：`./rl_real_imgo2 --log`（默认写 `./log`，可用 `--log-dir` 改）。
> 不改变任何控制行为：控制线程只把样本 memcpy 进环形队列，格式化与写盘在独立线程；队列满时丢掉最新样本并计数（`events.log` 末尾的 `dropped=`），绝不阻塞控制线程。

---

## 1. 文件与频率

| 文件 | 频率 | 内容 |
|---|---|---|
| `robot.csv` | **200 Hz**（每个控制节拍一行，`--log-every N` 可降为 200/N Hz） | 时间戳 + 设定 + 反馈 + 总线三段耗时（169 列） |
| `policy.csv` | **约 50 Hz**（每次消费到新策略结果一行） | PPO 输入 `obs[45]` + 输出 `act[12]`（67 列） |
| `events.log` | 事件驱动 | 状态切换、速度指令变化、Fault、退出、丢样本计数 |
| `meta.json` | 每次运行一份 | 自描述：关节映射/标签、标度、限幅、时序参数、列数 |
| `trace.exit.csv` / `trace.fault.csv` | 每次"发+收"一行（环形缓冲最近 16384 条） | 逐事务：`ok/waited_us/bytes/bad/stray`（`--log` 自动开启） |

实测（假总线）：200 Hz 时 1006 B/行 ≈ **200 KB/s ≈ 12 MB/min ≈ 720 MB/h**；`--log-every 2` 减半。
`--log-max-mb N`（默认 200）让 `robot.csv` 超限后自动切分为 `robot_002.csv`…

## 2. `robot.csv` 的 169 列（硬件顺序）

**顺序 = 总线顺序 × 每总线电机顺序**（`/dev/robot/leg_fl` 的 0/1/2，然后 leg_fr…），
与 `--trace`、接线、电机 ID 一致。`meta.json` 的 `joints` 给出每列的 `label/device/motor_id/direction`。

| 列 | 内容 | 单位 |
|---|---|---|
| `t_mono_ms` | 单调时钟（程序起点 0），算间隔用这个 | ms |
| `t_wall_ms` | Unix epoch 毫秒（和 `dmesg -T` 对齐） | ms |
| `tick` | 控制节拍序号 | — |
| `gen` | FSM 的策略代号（每次状态切换 +1） | — |
| `mode` | 0 InitialHold / 1 Standing / 2 StandHold / 3 PPO / 4 Crouching / 5 Passive / 6 Fault | — |
| `clamped` | 本次目标是否被 Safety 改过（1=改过） | — |
| `valid_mask` / `err_mask` | 12 位掩码：哪个关节反馈有效 / 有错误码 | bit0=第 0 个关节 |
| `cmd_vx/vy/wz` | **你设置的速度**（已按 `velocity_limits` 夹过） | m/s, m/s, rad/s |
| `kp_00..11`, `kd_00..11` | **实际下发**的增益（Safety 夹后） | N·m/rad, N·m/(rad/s) |
| `q_des_00..11` | **实际下发**的位置目标 | rad（输出侧） |
| `dq_des_00..11` | 速度目标（PPO 恒 0，仍记） | rad/s |
| `tau_ff_00..11` | 前馈力矩（PPO 恒 0，仍记） | N·m |
| `q_00..11` | 电机反馈位置（逻辑方向，= 控制用的 qL） | rad |
| `dq_00..11` | 电机反馈速度 | rad/s |
| `tau_00..11` | 电机反馈力矩 | N·m |
| `temp_00..11` | 电机温度 | ℃ |
| `age_00..11` | **每个关节各自的反馈年龄**（不是同一时刻采的！） | ms |
| `quat_w/x/y/z` | IMU 姿态（wxyz） | — |
| `gyro_x/y/z` | IMU 角速度 | rad/s |
| `imu_age_ms` / `imu_valid` / `imu_hz` | IMU 帧年龄 / 有效性 / 接收频率 | ms / 0·1 / Hz |
| `act_00..11` | 最近一次策略输出（**策略顺序**，便于和 `policy.csv` 对账） | — |
| `b0_total_us`…`b3_total_us` | 每条总线最近一轮 `cycle()` 的总耗时 | µs |
| `b0_flush_us`…`b3_flush_us` | 该轮"写之前清接收缓冲（`tcflush`）"的累计；**流水线模式下一轮只 flush 一次** | µs |
| `b0_write_us`…`b3_write_us` | 该轮"把 17 字节命令写进驱动"的**合计**（流水线模式含间隔，但计时只算 write 本身） | µs |
| `b0_reply_us`…`b3_reply_us` | **逐台模式**：各台"等应答+收字节+解析"的累计；**流水线模式**：从最后一条命令写完到全部收齐（收集阶段） | µs |

> **用来回答"一个事务 ~2 ms 到底花在哪"**：`bN_total_us ≈ bN_flush_us + bN_write_us + bN_reply_us + 少量代码开销`。
> 三段里谁占大头，就对应哪个环节：
> `flush` 大 → `tcflush` 贵（可改成失败后才 flush）；
> `write` 大 → 驱动/URB 写路径排队；
> `reply` 大 → 电机固件回复延迟或芯片攒包（换芯片也难救）。
> **流水线模式**（`MotorConfig::pipeline=true`，默认）：`write` 只算写入、`reply` 是"最后一发→全部收齐"，
> 所以 `reply` 应当约等于一个事务的芯片延迟（~1.6ms），而不是 3 倍。

**不记录**：IMU 的 rpy（可由 quat 推出）与加速度（PPO 不用）。

## 3. `policy.csv` 的 67 列（策略顺序）

| 列 | 内容 |
|---|---|
| `t_mono_ms,t_wall_ms,tick,gen,mode` | 同 `robot.csv`，用 `tick`/`t_mono_ms` 与主日志对齐 |
| `cmd_vx/vy/wz` | 该时刻的速度指令（obs 里的 commands 用它算出） |
| `obs_00..44` | **PPO 输入**，与策略实际输入同一个函数（`buildObservation`）生成 |
| `act_00..11` | 本次刚消费到的网络输出（已 clip） |
| `result_age_ms` | 该结果距今多久（> `result_timeout_ms` 会被判过期） |
| `obs_age_ms` | 构造该 obs 用的反馈快照距今多久 |

**约定**：`obs` 是供**下一次**推理使用的输入（其中 `obs[33..44]` 就是 `act` 的上一版）；
`act` 是本次刚拿到的输出。两者在同一行，便于看清"输入→输出"的对应关系。

### obs 的 45 维布局（也写在 `meta.json` 的 `obs_layout` 里）

```
0..2    gyro * ang_vel_scale(0.25)
3..5    projectedGravity(quaternion)
6..8    cmd * commands_scale
9..20   (q_pol[i] - default_pose[i]) * dof_pos_scale(1.0)
21..32  dq_pol[i] * dof_vel_scale(0.05)
33..44  上一版动作
最后统一 clamp 到 ±clip_obs(100)
```

## 4. 常用分析（pandas）

```python
import pandas as pd, json, glob
d = sorted(glob.glob('log/*/'))[-1]
meta = json.load(open(d + 'meta.json'))
r = pd.read_csv(d + 'robot.csv')
p = pd.read_csv(d + 'policy.csv')

# 反馈年龄：最老的那个关节（判断是否接近 100 ms 的 stale 阈值）
r['age_max'] = r[[f'age_{i:02d}' for i in range(12)]].max(axis=1)
r.nlargest(5, 'age_max')[['t_mono_ms', 'age_max', 'mode']]

# 命令跟踪误差（目标 vs 反馈）
for i in range(12):
    r[f'err_{i:02d}'] = r[f'q_des_{i:02d}'] - r[f'q_{i:02d}']

# 只取 PPO 段
ppo = r[r.mode == 3]
# PPO 输入与输出对账：obs[9..20] 应等于 (q - default_pose)
default = meta['config']['default_pose']
# policy ↔ hardware 映射：policy 顺序的第 i 个关节 = robot.csv 的 mapping[i] 列
mapping = meta['config']['policy_to_hardware']
```

## 5. 一个 `--log` 就够了（它自动带上另外两个诊断）

`--log` 打开后会**自动**再启用两样东西，不需要额外加参数：

| 自动启用 | 输出 | 用于 |
|---|---|---|
| `--bus-stats` | 每秒一行：每总线轮询 `last/max`、`线程最坏值 gap/body/interval`、`主控环迟到`、`IMU age=max` | 区分"**线程被抢占**"（`gap` 大）与"**I/O 慢**"（`body` 大） |
| `--trace` | 同目录下的 `trace.exit.csv` / `trace.fault.csv`：每次"发+收"一行 `t_ms,bus,id,ok,waited_us,bytes,bad,stray` | 区分"**没字节回来**（bytes=0）"、"**回了坏帧**（bad>0）"、"**串线**（stray>0）"、"**线程没跑**（某段时间完全没有记录）" |

两者仍可单独使用（老命令行不受影响），只是不用再记。

### 能定位什么、不能定位什么

| 问题 | `--log`（三个文件 + 自动 trace） | 说明 |
|---|---|---|
| 命令与反馈对不对、跟踪误差、是否顶到限幅 | ✅ | `robot.csv` 的 `q_des/q`、`clamped` |
| PPO 输入输出是否对齐、obs/结果有多旧 | ✅ | `policy.csv` 的 `obs/act/result_age_ms/obs_age_ms` |
| 状态机/按键/故障的时间线 | ✅ | `events.log` |
| 配置与关节映射的溯源（哪一列是哪个电机） | ✅ | `meta.json` |
| **USB↔485 链路静默**（一个字节都没回） | ✅（靠自动 trace） | `ok=0 waited≈20ms bytes=0` |
| **链路有噪声 / 坏帧** | ✅（靠自动 trace） | `bytes>0 bad>0` |
| **串线 / 收到别的 ID** | ✅（靠自动 trace） | `stray>0` |
| **总线线程被冻结/抢占** | ✅（靠自动 trace + bus-stats） | 某段时间 trace 没有记录，且 `gap` 很大 |
| **事务内阻塞**（如 `tcflush` 卡住） | ✅ | `waited_us` 明显大于 `io_timeout_us` |
| 电机是否"只对零指令应答、不对运动指令应答" | ✅ | 看失败事务前后 `ok` 的分布 + `robot.csv` 的 `age` |
| 电机内部故障（过流/过温/编码器） | ⚠️ 只能看到错误码 | `robot.csv` 的 `err_mask` + `temp`，具体码要看电机手册 |
| 485 电气指标（共模、压降、眼图） | ❌ | 需要示波器/万用表 |
| 电机内部 FOC 状态机 | ❌ | 不在本工程范围内 |

## 7. 已知边界

- `robot.csv` 的 12 个反馈值**不是同一时刻**采的（同一总线串行轮询，一轮约 5–6 ms；IMU 是另一个设备），
  所以每行都带 `age_00..11` 和 `imu_age_ms`——分析时不要把它们当成严格的"同一瞬间"。
- `policy.csv` 的 `obs` 用"当前快照 + 上一次动作"重建，是策略**下一次**会用的输入；
  推理线程实际消费的快照可能早 ≤20 ms，用 `obs_age_ms` 观察这个偏差。
- 队列满时会丢样本（正常不会），计数在 `events.log` 末尾和 stderr。
- 日志失败（磁盘满/无权限）只提示，不中断控制。
